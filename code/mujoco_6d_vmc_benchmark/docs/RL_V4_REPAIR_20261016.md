## 已确认的问题

1. **UTD配置没有控制真实更新次数**：旧trainer传给agent的是UTD1，但内层训练循环仍写死
   `range(2)`。43,656步checkpoint记录77,314次更新，恰为`2*(43656-4999)`；这不是两个
   critic各计一次的统计口径，而是实际调用了两次agent.update。修复版使用`range(utd)`。
2. **资源隔离没有落实**：旧wrapper的RSS监控只看轻量包装进程，没有覆盖trainer+simulator；
   它们继承app共享cgroup，memory.max和swap.max都是max。新恢复入口明确使用独立user
   systemd service的3GiB/禁swap硬限，trainer在启动时核验实际cgroup，拒绝软限制fallback。
3. **旧训练占用没有被正确识别**：v2 PID2156316在昨天14:03的11,000步/8回合后卡在保存，
   checkpoint未登记完成；本轮确认没有子模拟器，却仍占RSS1,182,588KiB。v3b的两个trainer
   PID2170717/2170718也仍真实训练，早期“已退出”的记录不符合当前宿主机事实。
   它们属于先前调参批次，不能把其进度当成当前v4，也不能仅归因于桌面应用占内存。
4. **停止顺序与保存间隔有缺陷**：之前先终止协调器导致v4整个启动容器中的进程提前消失，
   没有完成回合末保存；只每10k步保存使多个已结束回合无法恢复。修复版每个已结束回合均
   保存checkpoint；新service生命周期独立于启动shell。停止应请求trainer回合末退出，验证
   新checkpoint后才处置上级进程，不能先终止仍承载子进程的父容器。
5. **防重复/截止检查缺失**：新恢复入口在派发前检查宿主机旧RL进程、3GiB+768MiB余量、
   原截止、source/config/checkpoint hash，并以锁和独立尝试收据防重复派发。拒绝重用输出；
   没有自动acceptance入口，trainer也明确记录training_complete与ready_for_acceptance。
