# FLASK-style FR3 motion planning (development integration)

## What is reproduced

The paper's manipulator case treats the joint configuration as the
 differential-flat output, `y=q`, and uses the flat state `z=(q,q_dot)` with
pseudo-control `w=q_ddot`.  The fixed-time LQ minimum-acceleration boundary
value problem therefore has a closed-form cubic Hermite solution.  The new
`flask_joint_planner.py` implements that solution as `JointSegment`, samples
its closed-form `q`, `q_dot`, and `q_ddot`, and builds an RRT-style tree in
flat state space.  Each candidate edge is checked at a configurable set of
times for joint, velocity, acceleration, and caller-provided collision
constraints.

`MuJoCoFR3CollisionChecker` adapts the collision callback to a fixed-base
MuJoCo FR3/Panda model.  `flask_wbc.py` maps a returned `FlaskTrajectory` to
the existing `WBCCommand` contract: bounded joint feedback plus planned
velocity is converted to the current hand Jacobian and a reference FK pose.
This lets the existing VMC/compliance layer execute the trajectory without
changing its safety or observation boundary.

## Complex standalone scene

The current `run_sensor_wbc.py` wrapper builds a new cluttered MuJoCo scene at
runtime and does not load an SII benchmark environment. It contains a tabletop,
four legs, a rear shelf, upper and lower shelf boards, red and yellow boxes, a
blue cylinder, a green target cylinder, and a capsule obstacle that slides\sinusoidally along the side of the workspace. The target is a visual goal marker at `z=1.10 m`, above the end-effector goal
pose, with contact disabled for this tracking experiment; the other 12
`flask_*` obstacle geometries remain active in the planner and simulation. Sensors include
end-effector pose/twist, force/torque, accelerometer, gyroscope, table touch,
and all seven joint positions/velocities.

For the current scene the planner budget is 8,000 iterations with 40 samples per
segment. The execution trajectory is retimed by 3x to make the live plot legible.
The 2026-10-02 arm1 run found a one-segment plan in 0.73 ms and simulated 6.0 s
(3,000 steps) with zero contacts, `0.00796 rad` final joint error, and `28.06 Nm`
peak command torque. The JSON report is at
`/home/arm1/vmc_mujoco_runtime/flask_fr3_env_20261002_complex_sensor_wbc.json`.

The matching live plot was rendered from the same complex scene. Since the server
has no ffmpeg, it wrote 63 PNG frames to
`/home/arm1/vmc_mujoco_runtime/flask_fr3_env_20261002_complex_plot.frames/`; the
frames were encoded locally as `outputs/flask_fr3_realtime_plot_complex.mp4`.
The middle frame is a visual inspection artifact at
`outputs/flask_fr3_realtime_plot_complex_mid.png`.

## Real-time plot matching the reference video

`experiments/flask_fr3_env_20261002/render_realtime_plot.py` renders the new
scene frame by frame. The left panel is the MuJoCo FR3 view; the right panel is
updated online with `Speed + limit` and `Acceleration + limit`. The speed plot
contains normalized fastest-joint speed and end-effector speed; the lower plot
contains normalized fastest-joint acceleration and torque usage. A moving
vertical cursor marks the current simulation time.

The planner trajectory can be retimed with `FlaskTrajectory.retime(scale)`
without changing its geometric path. The earlier simple scene used `--time-scale 3`;
for the current complex scene the user-facing render uses `--time-scale 8`, giving
a 5.2 s planned trajectory and a 5.76 s video. On `arm1`, the complex renderer
produced 144 frames at 25 FPS under
`/home/arm1/vmc_mujoco_runtime/flask_fr3_env_20261002_complex_plot8.frames/`;
the server has no ffmpeg binary, so the script falls back to PNG frames. Those
frames were assembled locally into the user-facing video
`outputs/flask_fr3_realtime_plot_complex.mp4`.

Run it on a host with ffmpeg as:

```bash
MUJOCO_GL=egl PYTHONPATH=code/mujoco_6d_vmc_benchmark/scripts:code/mujoco_6d_vmc_benchmark/experiments/flask_fr3_env_20261002 \
```

The new `experiments/flask_fr3_env_20261002/run_sensor_wbc.py` creates a fresh
MuJoCo wrapper around a supplied FR3 asset. It does not load an existing SII
benchmark scene. The wrapper replaces position actuators with seven torque
motors, adds two obstacles, and registers end-effector frame, force/torque,
joint position, and joint velocity sensors. A computed-torque WBC tracks the
FLASK trajectory using `M(q)`, `qfrc_bias`, `q`, and `q_dot`, with the FR3
torque limits applied after the command is formed.

The arm1 run used `/home/arm1/vmc_mujoco_runtime/mujoco_menagerie/franka_fr3_v2/fr3v2.xml` as the upstream robot asset and wrote its result to
`/home/arm1/vmc_mujoco_runtime/flask_fr3_env_20261002_sensor_wbc.json`. The
planner found a two-segment collision-free trajectory in 3.86 ms; the WBC
simulation ran for 4.0 s / 2000 steps with peak command torque 48.57 Nm, zero
contacts, and final joint error 0.0644 rad. End-effector force/torque sensors
reported zero because the run intentionally did not make contact. This is a
simulated development result, not hardware validation.

The smoke uses a synthetic 7-DOF joint-space keep-out region to force a
multi-edge route.  It found a two-segment trajectory in 2.79 ms, duration
3.09 s, with zero sampled collisions, exact goal error 0, peak joint speed
2.56 rad/s (limit 2.61), and peak joint acceleration 8.89 rad/s² (limit
10).  The JSON is a development artifact at
`/home/arm1/vmc_mujoco_runtime/flask_fr3_20261002_smoke.json`; it does not
represent a MuJoCo geometry, hardware, or task-success result.

The focused regression tests are in
`tests/test_flask_joint_planner.py`.  They cover boundary conditions, direct
constraint checking, and a collision-forced sampling-tree route.  The server
image does not include `pytest`, so the three test functions were executed

of all three new modules also passed.

## Using a real FR3 scene

Construct `FlaskPlannerConfig` from the FR3 joint limits and call
`FlaskJointPlanner(config, collision_fn=MuJoCoFR3CollisionChecker(model, ...))`.
Pass the current `qpos[:7]`, `qvel[:7]`, and a joint goal to `plan`.  For
execution, instantiate `FlaskTrajectoryWBC` with the same model and hand body
ID and call `command(data, trajectory)` at the existing control rate.
Explicitly provide robot and obstacle geom names in safety-critical use;
inference by name prefix is intended only for development.

The implementation checks constraints at finite sample points, as does the
paper's vectorized collision-checking primitive.  A production deployment
still needs a denser/adaptive sampling policy, continuous swept-volume
margins, a scene-specific self-collision policy, and hardware validation.
The current smoke does not claim those guarantees and does not replace the
existing scaledWBC baseline until a paired FR3 scene evaluation is run.
